# OpenProse Windows native process host

This directory is an isolated, pinned Rust workspace for the small Windows-only
process host that both OpenProse CLI products can call. It contains no OpenProse
language semantics and no provider code. Its only job is to create, supervise,
observe, and tear down one external adapter process tree with native Windows
authority.

The current implementation is cross-checked but deliberately **not yet marked
strict on Windows**. A native Windows x64 CI run of the provider-free fixtures
is still required. The machine-readable status is
[`capabilities/windows-x64.v1.json`](capabilities/windows-x64.v1.json).

## Containment contract

For an admitted request the host:

1. accepts only an absolute, existing `.exe`; `.cmd`, shell, PowerShell, and
   implicit executable lookup are not supported;
2. accepts an explicit argument vector, working directory, closed environment,
   and base64 child stdin;
3. rejects an ambient wrapper recursion marker and rejects a child that aliases
   either the wrapper or this host by canonical path or Windows file identity;
4. creates three anonymous pipes and places only their child endpoints in a
   `PROC_THREAD_ATTRIBUTE_HANDLE_LIST`;
5. creates an unnamed Job Object with `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`;
6. invokes `CreateProcessW` with an explicit application name,
   `CREATE_SUSPENDED`, `CREATE_NEW_PROCESS_GROUP`,
   `CREATE_UNICODE_ENVIRONMENT`, and `EXTENDED_STARTUPINFO_PRESENT`;
7. assigns the still-suspended process to the Job, then and only then resumes
   its primary thread;
8. bounds stream bytes, read chunks, protocol lines, and in-memory queues;
9. tries the requested control grace (`CTRL_BREAK_EVENT` or none), then uses
   `TerminateJobObject`; and
10. retains the Job handle as authority, reports native exit status and Job
    accounting, and never infers tree ownership from a PID scan.

If assignment fails, the primary thread is still suspended and the host
terminates that process directly before returning an error. If the host itself
dies after assignment, closing the Job handle activates kill-on-close.

`CTRL_BREAK_EVENT` is best effort. It is not containment authority and its
delivery result is recorded separately. A nested-Job policy that prevents Job
assignment fails closed before resume.

The v1 request line is capped at 67,108,864 bytes. Its closed field limits are
16,777,215 decoded child-stdin bytes (22,369,620 base64 characters), 64 argv
items of at most 32,766 characters, 64 environment entries with 128-character
names and 8,192-character values, and 32,766-character absolute paths. The
Unicode environment block is independently capped at 4,194,304 bytes, and the
rendered Windows command line remains capped at 32,766 UTF-16 code units. Even
using the JSON worst case of a 12-byte escaped surrogate pair per schema
character, the maximum schema-shaped request is 55,083,084 bytes and therefore
fits the line boundary. A cancel control is capped at 4,096 bytes.

## Integration surface

Start `openprose-windows-process-host.exe` directly with redirected stdin,
stdout, and stderr. Do not put it behind a shell or PTY. Clear its ambient
environment, especially `OPENPROSE_RECURSION_TOKEN`.

- Write exactly one newline-terminated request JSON record to stdin, then keep
  stdin open. EOF with partial request bytes is malformed and never spawns.
- One later newline-terminated record may contain the versioned cancel control.
  It is terminal for control ingress. A malformed/partial control fails the run
  as `protocol-failure`; clean EOF means the caller disconnected and initiates
  cleanup.
- Read ordered event JSON lines from stdout. Child stdout and stderr remain
  distinct base64 events.
- Read stderr only for a bounded host-error JSON line. Environment values,
  child stdin, and argv are never included in host diagnostics.
- A host exit of `0` means the terminal event was emitted and the Job was
  observed empty. The child's native exit remains in `processExitCode`.
- Event sequence numbers are generated by a closed start/stream/terminal state
  machine. Event delivery never blocks the supervision loop: a full bounded
  queue is `OUTPUT_BACKPRESSURE`, while a missing reader is
  `OUTPUT_DISCONNECTED`; either condition fails the host closed.

`--version` prints the stable component/version pair. `--identity-json` prints
the closed `openprose.windows-process-host.identity/1` report with protocol IDs,
wire caps, target identity, and explicit false native-runtime/strict-readiness
claims. These probes never start a child and are available on non-Windows build
hosts as well.

The closed schemas are in [`protocol/`](protocol/). The caller must reject a
schema version it does not understand; there is no compatibility fallback.

## Test and audit commands

From this directory:

```text
cargo test --locked --all-features
cargo clippy --locked --all-targets --all-features -- -D warnings
python3 scripts/verify_static.py
cargo check --locked --target x86_64-pc-windows-msvc --all-targets --all-features
```

The final command needs the pinned Windows standard library but not a linker.
On a native Windows x64 worker, run:

```text
cargo test --locked --all-features
cargo clippy --locked --all-targets --all-features -- -D warnings
python scripts/verify_static.py
```

The `fixture` feature builds a provider-free child executable. The seven
Windows-only integration tests exercise exact process observations, whole-Job
cancellation, malformed-control and parent-disconnect cleanup with a descendant,
breakaway denial, output bounds, and both forms of recursion rejection. Every
spawned host has a 15-second test deadline and an unwind guard that kills and
reaps it; host death then closes the kill-on-close Job. The tests never invoke a
harness, model, network, or provider.

## Remaining promotion gate

Cross-compilation proves that the Windows-only code and tests type-check against
the pinned APIs. It does not prove runtime ordering, Job behavior, signal
delivery, handle inheritance, or teardown on Windows. Tier-1/strict promotion
therefore requires native Windows x64 CI evidence. After that evidence exists,
the Rust and Bun supervisors can separately integrate this helper through the
versioned protocol; this directory does not modify either product today.
