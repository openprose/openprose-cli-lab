# Bounded weave seed contract

This unpublished experiment ports a bounded subset of the [Python reference](../weave/README.md). It does not parse contracts, choose providers, resolve packages, or change the CLI. The shared fixtures below define its observable behavior before implementation.

`reconcile(binding, checkpoint, host, maxAttempts)` performs at most one action. Host capabilities are synchronous `observe`, `assess`, `act`, `save`, `clock`, and `newId`. Observation carries an opaque string payload, a caller-defined identity, observation time, exclusive expiry, and a gap flag. Assessment returns `satisfied`, `work-needed`, or `unknown`. The host must bind contract, evidence selector, policy and permissions into the binding and all relevant evidence into its identity.

A pending attempt returns `recovery-needed` without observing. Fresh identical evidence may reuse unexpired satisfaction only under the same binding. Otherwise assessment is followed by a new observation; changed identity or invalid freshness discards the assessment. Unknown and gaps never authorize action. Work-needed launches only within the cumulative attempt budget, after saving a pending checkpoint. Action failure preserves pending and returns `action-outcome-unknown`. Normal return clears pending and triggers observation and assessment again; it never establishes satisfaction itself. Save failures propagate and must prevent any subsequent action. Input checkpoints are copied.

`settlePending` (Rust `settle_pending`) accepts exact binding and pending attempt, a trusted `completed` or `not-applied` outcome and nonempty receipt reference. It returns a checkpoint with pending and cached satisfaction cleared, unchanged attempts, and the latest settlement retained. The caller must atomically save it. Settlement establishes neither fulfillment nor receipt authenticity.

The caller owns durable atomic saves, serialization, identity construction, authorization, scheduling, source freshness, provider calls, deadlines and costs. The core supplies no filesystem host, async runtime, distributed recovery, exactly-once effects, SDK packaging or CLI integration. Optional experimental local hosts and their JSON interchange are specified separately in HOST.md. Callback panics in Rust are outside the recoverable Result interface. No model reliability follows from deterministic parity.

## Shared black-box corpus

`fixtures/lifecycle.tsv` is tab-separated. Columns are name, initial checkpoint, observation sequence, assessment sequence, action outcome, attempt limit, expected status, disposition, attempts, pending, and expected observation/assessment/action/save counts. Initial states: empty, cached, expired, rebound, pending, exhausted. Cached identity is `a`, binding `v1`, expiry 100; expired expiry 9, rebound binding `v0`; pending/exhausted attempts 1. All clocks return 10. Observation tokens: `a`/`b` fresh identities, `g` gap, `f` observed at 11, `x` expiry 10. Assessment tokens: s satisfied, w work-needed, u unknown. Action is ok or fail. `-` means empty sequence or absent pending. Every act also asserts a saved pending record and incremented attempt count precede the effect. The corpus is intentionally small and readable; stress evidence for the Python prototype does not establish stress coverage for these ports.

## Type boundary and host errors

Both seeds restrict timestamps, clocks, limits and attempt counts to nonnegative integers no greater than 9,007,199,254,740,991. The Python prototype accepts additional finite timestamp values; this seed does not claim that broader input domain. Rust uses typed judgments and owned string evidence; Bun snapshots and freezes observation objects before assessment. Payloads are strings. Callback clock invocation counts are not part of shared parity and may differ from Python under an already stale observation.

Bun rejects thenables from synchronous callbacks. A thenable action result leaves the attempt pending with unknown outcome. Calling an accidentally asynchronous callback may already have started its work; rejecting its result cannot cancel it. Hosts must implement synchronous capabilities, including durable saves. Rust uses Result for fallible observe/assess/act/save methods. Observation, assessment and persistence errors propagate; only action errors become uncertain effects. Neither implementation catches process termination or supplies a durable failure receipt.
